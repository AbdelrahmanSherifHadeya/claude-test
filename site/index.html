Claude Code, day one

The short version of everything you need on your first day. Keep it open in a tab. Nothing here assumes you have written code before.

What it actually does

Ordinary chat hands you code to copy and paste. Claude Code has hands: it reads and writes real files, runs commands, runs your tests, and drives git and GitHub. You describe the outcome you want in plain English and it goes and does the work in an actual repository.

That difference is the whole thing. You are not asking for a snippet, you are asking for a change.

  • build from scratch
  • explain code you didn't write
  • fix bugs
  • write tests
  • rename things everywhere
  • review a diff
  • upgrade dependencies
  • write docs

Cloud or local

Two places to run it. Most people end up using both, for different moments.

Cloud

In a browser tab

  • Nothing to install
  • Runs on a temporary machine at Anthropic
  • Works from a phone
  • Fire off a task and walk away
  • Anything not pushed to GitHub is lost when it shuts down
Local

In your terminal

  • Install once, then type claude
  • Runs on your own machine
  • Sees your real files and your running app
  • Much tighter feedback loop
  • Where most day to day work happens

What to say to it

There is no special syntax. Plain English is the interface. Being specific about the outcome beats being technical about the method.

  • "Explain what this repo does, I didn't write any of it."
  • "Something is wrong with the login flow. Find out what and fix it."
  • "Add a dark mode toggle to the settings page."
  • "Write tests for the file I just changed."
  • "Rename userId to accountId everywhere, carefully."
  • "Walk me through this file line by line. I don't know Python."
  • "Break this on purpose so I can watch the tests catch it."

Plan mode

Plan mode makes Claude research first and propose a written plan, then stop and wait for you to approve it before touching a single file.

It is worth leaving on while you are new. You get to read what is about to happen and say no, and reading those plans is genuinely how you learn what the tool is capable of.

Ask for the check, not just the work. A plan that ends with "and then I will verify it" is worth more than one that ends with the change. Ask for something you can run yourself afterwards that tells you pass or fail, so you are never taking the summary on faith.

How the git part works

This genuinely is a sequence, so it is worth learning in order.

  1. Files change on diskYou or Claude edit something. Nothing is saved to history yet.
  2. git statusShows what changed but is not yet saved.
  3. git commitSaves a point in history, with a message explaining why.
  4. git pushUploads those commits to GitHub, so they exist off your machine.
  5. It appears on GitHubNow it is real, shareable, and survives your laptop dying.

A branch is a parallel line of history. Working on one means the main version stays untouched until you decide to merge your work in. That is why new work usually starts with a new branch.

When something looks wrong

You do not have to be able to read the code to catch a bad result. Three moves cover most of it:

  1. Run the project's own checksTests, linters, a verification script. Green or red is an answer that does not depend on anyone's opinion.
  2. Ask for a second pass/code-review reads the changes with fresh eyes and reports what it finds.
  3. Ask about the line you don't understandIf part of a change is opaque to you, that is a gap in the explanation, not in you. Ask.
The one habit worth forming. "It works" should mean a command was run and passed, not that someone said so. When you ask for a change, ask how you will know it worked. Any honest answer will point at something you can run.
